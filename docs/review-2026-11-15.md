# Review of 2026-11-15: what to fix

An independent review of the code (Claude Fable 5.2, at Ido's request) found the problems below.
This file turns each into work for the Claude session that develops Cerebro. Ido asked the review
to leave features still being built alone, so it covers the foundations: the reactive core, the
JSX runtime, the protocol, the host, the app's main process, saving, the language-server pool, the
index, terminals and agents' hooks.

## How to use this file

- **`CLAUDE.md`'s rules apply as for any work.** A fix comes with a test that fails without it,
  run before the fix to see it fail. A change goes through a pull request. A decision that changes
  is recorded in `decisions.md`.
- **Two kinds of item.** "To fix" items are bugs whose fix changes no decision: do them, in the
  order given. "To propose to Ido" items change a decision or reshape shared code: bring Ido a
  short proposal (what, why, what it costs), and build only on his word.
- **What's measured says so,** with the steps, so the same steps can become the failing test. The
  review's scripts weren't kept. Anything not marked measured was read from the code, or is a
  claim.
- **Line numbers are as of commit `ce8bf6a`** (`feat/cut-greyed`, 2026-11-14). Find by the names
  given where they've moved.
- **An item goes when it's done,** as in the backlog.

## To fix

### 1. Language servers aren't told that files changed on disk

**What's wrong.** The host's client sends a server `didOpen` and `didChange` only (`sync`,
`packages/host/src/lsp.ts:920`). `didClose` and `workspace/didChangeWatchedFiles` are sent
nowhere. So:

- a file sent once stays open in the server with the text it was last sent, and the server stops
  reading it from disk (in LSP an open file's text is the client's to give);
- a file never sent is read when the project loads, and nothing tells the server of later changes
  or of new files. Its `client/registerCapability` is answered and ignored (`:806`).

An agent editing files is the case Cerebro exists for. After it, the server answers from the old
state, and since it did answer, nothing is headed "Name matches" to warn.

**Measured** (TypeScript 7.0.2, through `LanguageServers`, patience raised to 15 s). A folder with
a `tsconfig.json` (`strict`, `include: ["*.ts"]`), `lib.ts` exporting
`area(width: number, height: number)`, and `main.ts` and `other.ts`, each importing it and calling
`area(2, 3)` on its line 2:

1. `problems` of `main.ts` gives none. `usages` of `area`, asked in `lib.ts`, gives `main.ts:2` and
   `other.ts:2`. That question sends `lib.ts`, so it's open in the server from here on.
2. `lib.ts` is rewritten on disk to `area(size: { width: number; height: number })`. Three seconds
   later `problems` of `main.ts` still gives none. It gives "Expected 1 arguments, but got 2."
   only after a question sends `lib.ts` with its new text.
3. A second call is added to `other.ts` on disk, and `added.ts` is created with a call. Three and
   eight seconds later, `usages` still gives the first two.

The other servers weren't measured.

**To do.** After a file changes on disk, or is created or deleted, the server's next answer
reflects it, without the server being started again (that reloads the whole project).

- A file no editor holds with unsaved edits shouldn't stay open in the server:
  `textDocument/didClose` gives it back to the disk.
- Changes to files that aren't open go as `workspace/didChangeWatchedFiles`.

**Measured since** (2026-11-15, TypeScript 7.0.2, the same three steps, through `LanguageServers`
with a `close` and a `changed` added to `LanguageServer`; the patch is not kept):

- `didClose` of `lib.ts` after step 2's rewrite: the next `problems` of `main.ts` gives "Expected 1
  arguments, but got 2." at once. Closed, a file isn't watched by the server itself: step 3's
  changes to files it never had open stay unseen without `didChangeWatchedFiles`.
- `workspace/didChangeWatchedFiles` for `other.ts` (changed) and `added.ts` (created), with
  `didChangeWatchedFiles` not declared in the client's capabilities: `usages` then gives all four.
  Declared with `dynamicRegistration: true`, the server registers `**/*` under the project's folder,
  its own `lib` folder, and `/tmp/**/*` (the project's parent); the answers are the same.
- Ten `problems` of `lib.ts`, closing it after each: 5 to 7 ms; kept open: 3 ms (a small project).

So the open-file half alone doesn't fix it: without a source of changed paths, a closed file goes
stale again on its next change. **Waiting on Ido:** that source is proposal B's question (a
watcher, or a status pass per worktree on a timer: an index pass is 4 to 5 git processes, and runs
today only when the index is asked something). Item 1 is built once he's chosen.

**Where the difficulty is.**

- The host doesn't know which files the page still shows or has edits in: every request carries
  the text, and nothing says a tab closed. Closing a file whose editor has unsaved edits would
  make answers about other files ignore those edits. Decide where that knowledge lives (the page
  saying when a document is no longer held, or the host comparing the text it's sent with the file
  on disk), and measure what opening and closing a file around a question costs before choosing.
- Where the changed paths come from. The index already works out each worktree's paths and
  content hashes on every pass (`indexWorktree`, `packages/index/src/worktree.ts`), so the
  difference between two passes is the changed, new and deleted paths at no new cost. It covers
  only the languages the index reads: not a changed `tsconfig.json` or `package.json`. Proposal B
  would be the fuller source.
- Whether TypeScript's server takes `didChangeWatchedFiles` from a client that doesn't declare
  `workspace.didChangeWatchedFiles.dynamicRegistration` and honour the patterns it registers isn't
  known: measure it.

**Done when** a real-server test in `packages/host/test/lsp.test.ts` (under "TypeScript 7's
server") runs the three steps and gets the error at step 2 and all four usages at step 3. It fails
today. Then the same for basedpyright and bash-language-server, or what was measured of each.

### 5. What the agent's status shows after an interrupt

The turn an interrupt cuts short is kept since 2026-11-15 (decision "Agent turns"): what's left is
its status. Read from the code, not measured: it stays "working" after an interrupt, until another
hook arrives (`HOOK_STATES`, `packages/host/src/agents.ts`). Claude Code's hooks reference lists no
hook for an interrupt. What `claude` runs after Esc (a `Notification` later, say) is to be
measured with the real CLI, as "Agent status and resuming" measured the others. If nothing runs,
what the status shows then is Ido's to say.

### 6. A save's check and its write are two requests

**What's wrong.** `save` (`packages/playground/src/documents.ts:261`) reads the file to see
whether it changed on disk (`:278`), runs the before-save hooks (`:287`, Prettier's formatting
among them), then writes (`:292`). What an agent writes to the file between the read and the write
is written over, with no conflict asked. Read from the code; not reproduced.

**To do.** The page says what it believes is on disk (a hash of the text it last read or saved
will do), and the host refuses the write when the file holds something else. The host's `fs.write`
(`packages/host/src/host.ts:559`) already reads the file just before writing it, for the Local
History. The page then treats the refusal as the conflict it is (`conflicts`, `documents.ts:51`).
That takes a read out of every save too.

**Where the difficulty is.** A failure's code and data don't reach the page: the main process
passes on its message alone (`handle`, `packages/app/src/ipc.ts:12`; proposal D). So "refused:
changed on disk" has to come back as an answer the page can tell apart, not as an error it would
have to read the words of.

**Done when** a host test writes over a file changed since the hash it gives, and is refused with
the file untouched; and a test in `packages/playground/test/documents.test.ts`, whose host changes
the file during a before-save hook, ends in the conflict's question and no write.

### 7. Every repository shares one "Repository" settings layer

**What's wrong.** In `packages/playground/src/settings.ts` the repository layer is made once
(`:250`), under the key `cerebro.settings.repo.cerebro` (`REPO`, `:231`), and `settingsFor` gives
it to every worktree of every project. "Settings" decided a layer per repository, shared by its
worktrees. Read from the code.

**Scenario.** Tab size set at Repository scope in one project shows, and applies, in every other.

**To do.** A layer per repository, found from the worktree's project. What's saved under the old
key belongs to no repository in particular: ask Ido whether it's dropped or given to one. The
settings files of "Settings" (`.cerebro/settings.json5`, through the host) aren't part of this:
proposal C is about where they'd land.

**Done when** a test in `packages/playground/test/settings.test.ts` sets a value at Repository
scope for a worktree of one project, and a worktree of another project doesn't see it.

### 8. `LineReader` copies more than it needs to

Measured, and small. (A terminal's buffer, the second place, was done with item 3.)

- **`LineReader`** (`packages/protocol/src/connection.ts:237`) joins each chunk to its buffer, and
  searches the whole buffer for a line's end again. One message arriving in 64 KB chunks took 6 ms
  at 1 MB, 111 ms at 5 MB, 473 ms at 10 MB and 901 ms at 14 MB (a 10 MB image in base64, as
  `fs.readBytes` answers). That's paid in the host, and again in the app's main process, which
  serves every window. Search only what's new, and join once a line is whole.

**Done when** its tests still pass, and the same measurements are given before and after. A
test of time alone would be flaky in CI (`testing.md`): if one is added, it compares two sizes in
the same run, not against a fixed limit.

### 9. An effect's first run isn't batched

**What's wrong.** `effect` (`packages/reactive/src/core.ts:372`) runs a new effect outside a
batch. A write it makes to something it has read flushes at once, while its sources are still
those from before the run (none), so it isn't run again, and is left with the old value. Inside a
batch, or another effect's flush, the same effect is run again as it should be.

**Measured.**
`const count = signal(0); effect(() => { if (count.get() < 5) count.set(count.get() + 1); })`
leaves `count` at 1, after one run. Created inside `batch(…)`, it leaves 5, after six runs. The
test "settles when it writes a value it reads" passes either way: one write settles it.

**To do.** The first run in a batch, as every later run is. Check that the JSX runtime's bindings
and regions (`packages/jsx/src/owner.ts`, `dom.ts`), which make effects while rendering, behave as
before.

**Done when** the measurement above is a test in `packages/reactive/test/core.test.ts`, giving 5
and six runs outside a batch.

### 10. `README.md` and `architecture.md` describe an earlier project

- `README.md:4-6` says milestone 1 is in progress, and lists four finished parts.
- `docs/architecture.md:3-4` says all but the spike "is not built yet". Its package table
  (`:28-37`) has features in `plugins/*`, the host "assembled from host-side packages" and
  "message types" in `protocol`; `:50` has a session database in the host.

In the code, the features are `packages/playground/src` (84 files, 28,841 lines), two plugins
exist (Notes and Prettier), the host is one package, `protocol` is the transport alone, and
agents' session ids are in the page's storage (`packages/playground/src/agents.tsx:22`).

**To do.** Bring both up to date with what's built. Every new session reads them first, so a
wrong picture there costs each one. Where the code departs from what `architecture.md` set as the
aim (features as plugins, state in the host), say what's built, and leave the aim to Ido
(proposal H).

### 11. Smaller things

Each with a test that fails first.

- **`ObservableArray.set` and the other collections' writes**
  (`packages/reactive/src/collections.ts:64`) change the collection, and then `emit` throws if a
  computed value is running ("A computed value must not write"): the collection is changed, with
  nobody told. Check before changing, as `Signal.set` does.
- **`readFileBytes`** (`packages/host/src/files.ts:68`) ignores how many bytes `read` gave. A file
  that shrinks between the `stat` and the `read` (an agent rewriting it) comes back padded with
  NUL bytes.
- **`listFolder`** (`packages/host/src/files.ts:36`) lists a symbolic link to a folder as a file:
  `isDirectory` is false for a link.
- **`IndexService.files`** (`packages/host/src/index-service.ts:70`) counts a pass's 2 seconds
  from its start: while a pass longer than that runs, every question starts another over the same
  index.
- **`PluginRegistry.add`** (`packages/plugin-api/src/plugins.ts:170`): a plugin removed while its
  `activate` awaits keeps what it registers after, with nothing left to remove it.
- **Fourteen `ui-*` packages' tests** import `@cerebro-ide/theme` without declaring it (the open
  question "Undeclared dependencies"). Every `src` import is declared.

## To propose to Ido

### A. A host that dies goes unnoticed

When a host exits unasked, the app closes its connection (`child.on('exit')`,
`packages/app/src/host.ts:64`) and does nothing else. The page isn't told, its requests fail with
"Connection closed", and the project's terminals, its agents among them, have ended with no word
in their views (read from the code). Nothing in the host catches a rejection nobody handles, which
ends a Node process. To propose: what the page shows (a notification, the terminals saying their
process ended), and whether the app starts the host again, its agents resumed by their session ids
as after a restart.

### B. One source of "these files changed", instead of a timer per view

Seven timers in the page ask the host, each on its own: the open documents, the Project tree, the
repository's state, the Commit window, Agent Changes, the shelf, and the Local History.

**Measured** on Linux, with the host's own code and a `git` that counts: a tree with its root and
20 folders open, `git.changes`, `agent.turns` and `git.state` cost 32 git processes a cycle (21 of
them one `git check-ignore` per folder, 9 of them `git.state`), which is 16 a second while the
window has the focus. Windows wasn't measured; `decisions.md` has a dozen git processes at over a
second there.

Read from the code: every document opened in a session is kept (`documents`,
`packages/playground/src/documents.ts:65`; only a deleted file's is dropped), and its whole text
is read again every 2 seconds, whether a tab shows it or not, and after its project has closed.

"The project tree" marks polling as Claude's choice, open to change. To propose: the host telling
the page which paths changed (from a watcher, or from one status pass per worktree), for the tree,
the documents, the Commit window, the index and item 1 to share. If Ido keeps polling, two steps
change nothing the user sees: one `git check-ignore` for all of a refresh's folders together, and
a document's size and time checked before its text is read. Letting go of documents no tab shows
would change "Editing and saving", where a document outlives its tabs: his call too.

### C. Storage behind one module

29 files of `packages/playground/src` call `localStorage` themselves, each with its own key:
settings at every level, the layout, keymaps, agents' session ids, bookmarks, terminals. "Settings"
and "The layout persists" keep the browser's storage "until the host's local database exists";
each feature since has added a call site to move then. Two windows share the storage and neither
listens for the other's writes, so a window saving a whole layer undoes the other's change (read
from the code). To propose: one module that owns the keys, the reading and the writing, so the
host's database and the settings files can replace it in one place.

### D. Types for the protocol's methods

`serveOn` registers 138 methods and checks each one's parameters by hand. The page has about 170
call sites naming methods as strings, with about 150 casts of what comes back. A changed shape
compiles on both sides; the page's unit tests answer from `FakeHost`, so only the e2e tests would
see it. Names already differ for the same thing: `git.authors` takes `worktree`,
`git.exclusiveAuthors` takes `path`. A failure's code and data stop at the main process (`handle`,
`packages/app/src/ipc.ts:12`): the page gets the message alone. To propose: a map of each method
to its parameters and result, types only, in `protocol`, which `onRequest` and `request` take,
adopted a method at a time.

### E. The index off the host's event loop

The host's one event loop serves terminals and the prompt's hook, and parses the index too: 200
files between yields (`BATCH`, `packages/index/src/worktree.ts:42`), which by `decisions.md`'s
14 s for 5,231 files is about half a second a batch (derived, not measured). The cache is written
whole after each pass that parsed something (0.37 s there). To propose: the index in a worker
thread; the spike measured it on 8.

### F. Where an effect's error goes

An effect that throws makes the write that triggered it throw (pinned by the test "keeps running
other effects when one throws, then throws the first error"). So a view's failing binding can fail
an unrelated action: in `save`, `doc.saved()` is inside the `try`
(`packages/playground/src/documents.ts:297`), and would report "Couldn't save" for a file that was
written (read from the code). Whether errors reach writers or are reported apart is a decision
("The MobX-style API").

### G. The file's text with every language-server question

"Language servers, first part" sends the file's text with each request. Highlights, problems,
folds, structure, markers and completions are asked as one types, each carrying the text through
the app's main process to the host. Not measured. It matters most for the host over `ssh`
(milestone 3). To propose: the text sent once per change, and questions naming its version.

### H. Features as plugins

`architecture.md` has features in `plugins/*`, built against `plugin-api` as a third party would
build them. They're in the page, and `plugin-api` has the contribution points Prettier needed. No
restructuring is asked for: the question for Ido is whether that's still the aim, so
`architecture.md` can say (item 10).

## What the review found sound

So it isn't done again:

- no cycles between packages, nothing depends on the playground, and every `src` import is
  declared;
- no `innerHTML` or the like anywhere, under the page's Content-Security-Policy;
- coverage at 100% per file, with no ignore comments and no retries. What it can't see is time and
  the boundaries between processes, which is where the items above are: each needs its scenario as
  a test.

## What it didn't cover

The features still being built (the newer git dialogs, scratch files, bookmarks, cut and paste,
the Structure and Hierarchy windows); the editor and layout UI packages line by line; the macOS
native module; the e2e tests. Of the backlog's 27 known gaps, 23 are tests that fail now and then
with no cause found: that items 2 and 3 (the host killed, the terminal output's races: both done)
explain some of them is a claim.
